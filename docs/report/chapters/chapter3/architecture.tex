\section{Conception générale}

La conception générale présente l'organisation physique et logique de la
plateforme. Elle fixe les responsabilités des grandes parties du système avant
d'aborder les scénarios détaillés. Le choix retenu privilégie une séparation
claire des responsabilités tout en restant compatible avec la durée du stage et
une réalisation individuelle.

\subsection{Architecture physique}

\subsubsection{Architecture client--serveur}

\ProjectName{} adopte une architecture client--serveur. Le navigateur constitue
le client de l'application web et communique avec le serveur applicatif au moyen
de requêtes HTTPS et de réponses JSON. Le serveur applique les règles métier,
contrôle les autorisations et reste le seul composant autorisé à modifier les
données persistantes.

La communication avec les équipements forme un second échange client--serveur.
Les bornes, physiques ou simulées, ouvrent une connexion WebSocket avec une
passerelle OCPP. Celle-ci adapte les messages du protocole au système
d'information sans accéder directement à la base de données. Cette séparation
évite de mélanger les connexions longues des équipements avec les requêtes web de
l'application.

\subsubsection{Architecture trois tiers}

L'application est organisée selon une architecture trois tiers :

\begin{description}[leftmargin=35mm,style=nextline]
  \item[Présentation] interfaces, formulaires et visualisations exécutés dans le
  navigateur ;
  \item[Application et métier] cas d'utilisation, validation, autorisation,
  disponibilité, recharge, maintenance, tarification et facturation ;
  \item[Persistance] données relationnelles et transactions garantissant la
  cohérence durable des informations.
\end{description}

Cette séparation limite les dépendances entre l'interface et les règles métier.
Une modification visuelle n'affecte pas la persistance, tandis qu'une évolution
d'une règle de disponibilité ou de tarification peut être validée sans dépendre
de l'affichage.

\subsubsection{Architecture logicielle}

Le coeur applicatif suit le style d'un \textbf{monolithe modulaire}. Les fonctions
sont déployées dans une même application et partagent une base relationnelle,
mais elles sont regroupées par domaines : identité, organisations, stations,
OCPP, recharge, exploitation, commerce et rapports. Ce choix simplifie les
transactions tout en évitant de concentrer les règles dans les contrôleurs.

Le backend applique une \textbf{architecture en couches}. Les contrôleurs adaptent
les échanges HTTP, les objets de validation contrôlent les entrées, les policies
autorisent les actions, les services exécutent les cas d'utilisation et les
modèles assurent la persistance. Il s'appuie sur le patron \textbf{MVC}, adapté au
contexte d'une API : la présentation est confiée au frontend, tandis que le
backend expose des ressources JSON.

Le frontend adopte une architecture \textbf{orientée composants}. Les pages
composent des éléments réutilisables et regroupent les accès aux données par
fonctionnalité. Le patron \textbf{Adapter} isole les services externes derrière
des contrats remplaçables. Enfin, une approche \textbf{orientée événements}
sépare les messages OCPP reçus des états métier calculés.
