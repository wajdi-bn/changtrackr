\section{Conception générale}

La conception générale décrit l'organisation physique du système, ses couches
logiques et les responsabilités de ses principaux composants. Elle privilégie une
séparation nette des responsabilités sans introduire la complexité d'une
architecture distribuée complète, peu adaptée à la durée du stage et à une
réalisation individuelle.

\subsection{Architecture physique}

\subsubsection{Architecture client--serveur}

\ProjectName{} adopte une architecture client--serveur. Le navigateur constitue le
client et exécute l'application React. Il communique avec l'API Laravel au moyen de
requêtes HTTPS et de réponses JSON. Les mises à jour temps réel sont diffusées par
WebSocket au moyen de Laravel Reverb. Le serveur applicatif applique les règles
métier, contrôle les autorisations et reste l'unique composant autorisé à modifier
les données persistantes.

La communication avec les bornes constitue un second échange client--serveur. Les
bornes ou leur simulateur se connectent à une passerelle WebSocket au moyen du
protocole OCPP 1.6 JSON. La passerelle traduit les messages du protocole en
événements normalisés, puis les transmet à Laravel par une API interne signée. Elle
n'accède jamais directement à la base de données.

\subsubsection{Modèle trois tiers}

L'application est organisée selon un modèle trois tiers :

\begin{description}[leftmargin=35mm,style=nextline]
  \item[Présentation] pages, composants, formulaires et visualisations exécutés dans
  le navigateur ;
  \item[Application et métier] cas d'utilisation, validation, autorisation,
  tarification, disponibilité, recharge, maintenance et facturation ;
  \item[Persistance] modèles relationnels et transactions assurant la conservation
  cohérente des informations dans PostgreSQL.
\end{description}

Cette séparation limite les dépendances entre l'interface et les règles métier. Une
modification visuelle n'affecte pas la persistance, tandis qu'une nouvelle règle de
disponibilité ou de tarification peut être testée indépendamment de l'affichage.

\subsection{Architecture logique}

\subsubsection{Styles et patrons de conception}

Le coeur applicatif est réalisé sous la forme d'un \textbf{monolithe modulaire}.
Les fonctionnalités sont déployées dans une même application Laravel et partagent
une base PostgreSQL, mais elles sont séparées par domaines : identité,
organisations, stations, OCPP, recharge, exploitation, commerce et rapports. Ce
choix conserve la simplicité des transactions locales tout en évitant de concentrer
les règles dans les contrôleurs.

Le backend applique une \textbf{architecture en couches}. Les contrôleurs adaptent
HTTP, les requêtes dédiées valident les entrées, les policies autorisent l'action,
les services exécutent le cas d'utilisation, puis les modèles Eloquent assurent la
persistance. Laravel repose bien sur le patron \textbf{MVC}, mais, dans ce projet,
la vue HTML n'est pas rendue par Laravel : React prend en charge la présentation et
les contrôleurs Laravel renvoient des ressources JSON. Le terme MVC décrit donc
principalement l'organisation du backend.

Le frontend utilise une architecture \textbf{orientée composants}. Les pages
composent des composants réutilisables, tandis que les accès API, les types et les
requêtes sont regroupés par fonctionnalité. Enfin, deux patrons complètent cette
organisation :

\begin{itemize}[leftmargin=7mm]
  \item le patron \textbf{Adapter} isole Google OAuth, Resend, la cartographie et le
  paiement derrière des contrats remplaçables ;
  \item une approche \textbf{orientée événements} traite les messages OCPP, les
  changements de disponibilité, les alertes et les notifications sans confondre
  l'événement reçu avec l'état métier calculé.
\end{itemize}

\subsection{Description des composants}

\subsubsection{Application web React}

L'interface est une application monopage développée avec React et TypeScript
\cite{react}. Vite assure le développement et la compilation. Ant Design fournit
les contrôles d'interface ; TanStack Query gère l'état provenant du serveur ; Axios
centralise les appels HTTP. React Router sépare les routes publiques et protégées.
Leaflet et OpenStreetMap affichent les stations et permettent de sélectionner une
position \cite{leaflet,openStreetMap}. Recharts produit les graphiques et Laravel
Echo consomme les événements diffusés par Reverb.

Les appels API sont regroupés par fonctionnalité hors des composants visuels.
L'état serveur reste géré par TanStack Query, tandis que les états temporaires
d'interface, comme l'étape d'un assistant, restent locaux au frontend.

\subsubsection{API et coeur métier Laravel}

Laravel 13 expose l'API REST, valide les entrées, applique les autorisations et
orchestre les cas d'utilisation \cite{laravel}. Une requête protégée traverse les
responsabilités suivantes :

\begin{enumerate}[leftmargin=8mm]
  \item Sanctum identifie la session et contrôle le jeton CSRF ;
  \item le middleware organisationnel vérifie le statut et le périmètre du compte ;
  \item une \emph{Form Request} valide et normalise les données ;
  \item une policy vérifie l'action sur la ressource concernée ;
  \item le contrôleur délègue l'opération à un service métier ;
  \item le service applique les invariants, transactions et événements ;
  \item une API Resource structure la réponse exposée.
\end{enumerate}

Les services couvrent notamment le commissioning, la disponibilité, les
transactions OCPP, les sessions, le paiement, la maintenance, les notifications,
les abonnements et les exports. Les contrôleurs demeurent ainsi des adaptateurs
HTTP et non des conteneurs de logique métier.

\subsubsection{Persistance, asynchronisme et temps réel}

PostgreSQL 16 stocke les comptes, actifs, événements techniques, projections,
transactions et journaux \cite{postgresql}. Les opérations atomiques, telles que la
création d'une station avec ses connecteurs ou l'enregistrement d'une transaction
OCPP, sont protégées par des transactions de base de données. La file d'attente et
le cache de l'environnement de référence utilisent également PostgreSQL.

Le worker exécute les emails, notifications et opérations différées. Le scheduler
recalcule la disponibilité, expire les commandes OCPP, génère les maintenances
récurrentes, vérifie les SLA et synchronise les abonnements. Reverb diffuse ensuite
les changements sur des canaux privés associés à un utilisateur, une organisation
ou une session.

\subsubsection{Passerelle OCPP}

La passerelle est développée en Python avec les bibliothèques \texttt{ocpp},
\texttt{websockets} et \texttt{httpx}. Elle accepte les connexions
\texttt{ocpp1.6}, authentifie l'identité de la station auprès de Laravel, publie
chaque message normalisé et récupère les commandes distantes. Elle supporte
notamment \texttt{BootNotification}, \texttt{Heartbeat},
\texttt{StatusNotification}, \texttt{Authorize}, \texttt{StartTransaction},
\texttt{MeterValues} et \texttt{StopTransaction}.

La passerelle prend également en charge les commandes distantes suivantes :
\begin{itemize}[leftmargin=7mm]
  \item \texttt{RemoteStartTransaction} et
  \texttt{RemoteStopTransaction} pour piloter une recharge ;
  \item \texttt{Reset}, \texttt{UnlockConnector} et
  \texttt{ChangeAvailability} pour l'exploitation de la station.
\end{itemize}
OCPP 1.6 JSON correspond au simulateur et au périmètre du stage
\cite{ocaOcpp16,sapSimulator}. OCPP 2.0.1 demeure une perspective.

\subsection{Architecture logicielle}

\subsubsection{Organisation du frontend}

Le frontend suit une organisation par fonctionnalités :

\begin{itemize}[leftmargin=7mm]
  \item \texttt{features/auth} regroupe la session et les gardes de routes ;
  \item \texttt{features/stations}, \texttt{maps} et \texttt{charging} portent les
  parcours de station et de recharge ;
  \item \texttt{features/operations} couvre alertes, interventions et maintenance ;
  \item \texttt{features/commercial}, \texttt{subscriptions} et \texttt{tariffs}
  séparent les deux niveaux de commerce ;
  \item \texttt{features/realtime} encapsule Echo et Reverb ;
  \item \texttt{pages} compose ces modules sans réimplémenter leurs contrats API.
\end{itemize}

L'interface construit ses menus et tableaux de bord à partir du rôle retourné par le
backend. Cette adaptation améliore l'expérience, mais ne constitue pas une barrière
de sécurité : toute route masquée reste protégée par Laravel.

\subsubsection{Organisation du backend}

Le backend respecte les responsabilités natives de Laravel :

\begin{description}[leftmargin=35mm,style=nextline]
  \item[\texttt{Http/Controllers}] adaptation des requêtes et réponses ;
  \item[\texttt{Http/Requests}] validation, normalisation et préconditions ;
  \item[\texttt{Policies}] autorisation par action, rôle et organisation ;
  \item[\texttt{Services}] orchestration transactionnelle et règles métier ;
  \item[\texttt{Models}] relations, attributs et invariants locaux ;
  \item[\texttt{Jobs/Events}] traitements asynchrones et diffusion temps réel ;
  \item[\texttt{Contracts}] interfaces des intégrations remplaçables.
\end{description}

L'interface \texttt{PaymentGateway} illustre cette séparation. Les services de
recharge appellent les opérations d'autorisation, de capture, de libération et de
débit sans dépendre de WireMock. Un futur adaptateur ClicToPay, e-DINAR/D17,
GPGCheckout, Konnect ou Flouci pourra respecter le même contrat.
